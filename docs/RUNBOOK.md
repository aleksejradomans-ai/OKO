# RUNBOOK: проверка, карта доказуемости, типовые сбои

Обезличенный порядок действий для любого, кто собирает и проверяет движок. Без привязки к машине: команды — из корня
репозитория, пути — относительные. Каждый раздел: сверху чертёж (команды, файлы, что считается успехом), снизу —
по-человечески.

## 1. Полный прогон тестов

### Чертёж

```
python -m pytest src -q -p no:cacheprovider -rxs --junitxml=pytest_src.xml
python -m pytest test_data_hygiene.py tools/test_calibrate_sigma.py tools/test_check_sigma_2e.py -q -p no:cacheprovider -rxs --junitxml=pytest_extra.xml
```

- Успех: код возврата 0; ожидаемые падения — ровно `.github/known_xfail.txt`; пропуски — ровно
  `.github/known_skips.txt` (Windows) или `.github/known_skips_linux.txt` (Linux).
- Сторож ослабления тестов: `python tools/weakening_guard.py --base auto --head HEAD --collect --allow .github/test_weakening_allow.txt`
  (база — опубликованный коммит: нужен `refs/remotes/origin/oko-live`)
  — 0 красных находок.

### По-человечески

Тесты — это автоматическая проверка, что движок ведёт себя так, как обещано. Если тест убрали или ослабили, сторож
это заметит: «проверка прошла» не должна означать «проверку выключили».

## 2. Карта доказуемости

### Чертёж

- Источник: `docs/control_map.csv` (колонки `id,implementation,tests,evidence,scope,known_gap`), зоны и пометки
  «Зачем это владельцу» — таблица «Уровни контроля» в `docs/INVARIANTS.md`, строки «что сломается» —
  `docs/control_map_plain.csv`.
- Проверка по отчётам обеих платформ:
  ```
  python tools/verify_control_map.py --junit windows=<win>/pytest_src.xml --junit windows=<win>/pytest_extra.xml --junit linux=<lin>/pytest_src.xml --junit linux=<lin>/pytest_extra.xml --check-md docs/CONTROL_MAP.md
  ```
- Перегенерация карты после правки csv (те же `--junit`):
  `... --write-md docs/CONTROL_MAP.md` — без `--generated-on` (строка «Сгенерирован на» без SHA) или
  `--generated-on <SHA>` только с SHA ОПУБЛИКОВАННОГО снимка (`oko-live` / `main`). SHA родителя из локальной истории
  может быть приватным коммитом — его в публичную карту не писать.
- С одним отчётом верификатор печатает «проверено на 1 платформе из 2» и PASS не выдаёт.
- В CI три обязательных job: `pytest-windows`, `pytest-linux` и `control-map`. Шаг `control map (this platform)`
  каждого джоба pytest красный при любом подтверждающем тесте не в PASS на своей платформе; job `control-map` (после
  обоих, `if: always()`) считает карту по JUnit ОБЕИХ платформ из их артефактов и сверяет `docs/CONTROL_MAP.md` со
  свежей картой. Все три зелёные — каждый подтверждающий тест прошёл на обеих платформах и карта свежая.
- Правка `.github/workflows/` без строки согласия охраняемой зоны (`.github/guarded_change_allow.txt`, см.
  `docs/GUARDS.md`) — нарушение верификатора (B33).
- Тест `src/test_verify_control_map.py` сверяет `docs/CONTROL_MAP.md` со свежей картой: карту не перегенерировали —
  красный тест.

### По-человечески

У каждого правила движка есть запись: где в коде оно живёт, какие тесты его проверяют и насколько эти тесты
убедительны. «Тест читает исходник» — слабое доказательство, и карта честно называет его `source-scan`. Если тест
правила упал, пропущен без объяснения или помечен как ожидаемое падение — правило считается неподтверждённым.

## 3. Типовые сбои верификатора

| сообщение | что значит | что делать |
|---|---|---|
| `ID не 1-в-1` | в карте нет правила из `docs/INVARIANTS.md` или есть лишнее | добавить или убрать строку в `docs/control_map.csv` |
| `нет файла` / `нет символа` | код переименован или удалён | исправить `implementation`; если правило больше не исполняется — это вопрос владельцу, а не правка карты |
| `MISSING` | тест не найден в отчёте | тест переименован или не запускается; исправить `tests` |
| `SKIP` без known_gap | тест пропущен на платформе | записать пропуск в `known_gap` (статус станет GAP) или вернуть тест на платформу |
| `XFAIL` / `XPASS` / `в known_xfail` | тест помечен как ожидаемое падение | убрать его из `tests`, описать пробел в `known_gap` |
| `читает исходник` | тест с `behavior` / `integration` читает код | поставить `source-scan` или найти поведенческий тест |
| `kernel_codes.txt расходится с реестром` | служебный код добавлен в код, но не в справочник (или наоборот) | обновить `docs/kernel_codes.txt` |
| `карта устарела` | `docs/CONTROL_MAP.md` не совпадает со свежей | перегенерировать карту (раздел 2) |

### По-человечески

Красный верификатор почти всегда означает одно из двух: код поменялся, а запись о правиле — нет, или проверка правила
стала слабее. В обоих случаях чинится запись или тест — но не так, чтобы правило «прошло» без настоящей проверки.

## 4. Публикация и откат

### Чертёж

- Публикуется только снимок дерева, прошедший скан перед публикацией (локальные пути, имена машин и служб, адреса
  сети, ключи — находка = остановка без публикации).
- Публикация двухступенчатая: сначала ветка `ci/<sha12>` и CI на ней, затем перенос того же коммита в публичные ветки
  без force.
- Откат опубликованного: отдельный коммит-отмена через ту же двухступенчатую публикацию; историю не переписывать.

### По-человечески

Наружу уходит только проверенный код, и сначала его проверяет CI. Ошибку исправляют новым коммитом, а не
стиранием истории: так всегда видно, что и когда поменялось.
