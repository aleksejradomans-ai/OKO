# Состояние карантина: суточный слепок, недельный слепок, зум

Модуль `src/quarantine_state.py`, CLI `tools/quarantine_state_cli.py`. Только стандартная библиотека; в службы не встроен,
расписание запуска — отдельно. Хранилище — отдельная SQLite-база (по умолчанию `data/state/quarantine_state.db`,
переопределение — `OKO_QUARANTINE_STATE_DB`).

## Вход

Каталог карантина: перенесённые файлы с сохранением относительных путей и `manifest.tsv`
(столбцы `path`, `size`, `sha256`, `reason`, `moved_at`, `quarantine_path`). Категория файла выводится из `reason`
по ключевым словам: `duplicate` (дубль / лишняя копия), `merge_source` (исходник склейки), `old_version`
(старая версия), `test_junk` (тестовый мусор / сирота без записи базы), иначе `other`; файл без строки манифеста —
`unlisted`.

## Уровень 1 — суточный слепок (`snapshot <dir>`)

Агрегат без содержимого и без имён файлов: число файлов и байт, файлы и байты по категориям, расширения,
`time_min` / `time_max` переноса (по манифесту, иначе mtime), число строк манифеста, `content_digest` —
sha256 от отсортированного списка sha256 файлов. Канонический JSON агрегата → `aggregate_sha256`;
`daily_uuid = uuid5(NAMESPACE, sha256(канонический JSON {day, dir, aggregate_sha256}))`,
`NAMESPACE = uuid5(NAMESPACE_URL, "oko:quarantine_state")`. Таблица `quarantine_state_snapshots`
(`daily_uuid` PK, `day`, `dir`, `created_at`, `aggregate_json`, `aggregate_sha256`, `ttl_h`, `purged_at`).
Повтор в те же сутки с тем же агрегатом — та же строка.

## Очистка (`purge <dir> [--dry-run]`)

Каталог удаляется только при двух условиях одновременно: есть слепок того же каталога с тем же агрегатом
(агрегат пересчитывается перед удалением) и возраст карантина (`now − time_max`) не меньше `ttl_h`
(по умолчанию 24 ч). Иначе — 0 удалений и причина: `no_snapshot`, `directory_changed_since_snapshot`,
`age_below_ttl`, `dry_run_would_delete`, `no_directory`, `refused_path` (корень диска, домашний каталог,
каталог с самим модулем).

## Уровень 2 — недельный слепок (`weekly [--end-day D] [--k 3]`)

Окно — 7 суток, заканчивая `end_day`; на сутки берётся последний слепок. Ряды метрик: `files`, `bytes`,
`cat.<категория>.files`, `cat.<категория>.bytes`. `weekly_uuid = uuid5(NAMESPACE, sha256(канонический JSON
{daily: [daily_uuid по дням], aggregate: {days, series, k}}))`; `partial = 1`, если суток меньше 7.
Точка спада — сутки, где значение метрики ниже медианы окна больше чем на `k · scale`; `scale` — MAD
(медиана абсолютных отклонений), при MAD = 0 — `max(1, 5 % медианы)`; при меньше чем 3 сутках правило не
применяется. Таблица `quarantine_state_weekly`.

## Уровень 3 — зум (`zoom <weekly_uuid>`)

Для каждой точки спада: сутки, `daily_uuid`, суточный агрегат и узлы отклонения — метрики и категории
(значение, медиана окна, разность). Окно сужается с недели до суток и до категории.

## Цикл расписания (`cycle --root DIR [--glob knowledge_*] [--weekly-on Sun|none] [--dry-run] [--log P]`)

Один проход для каждого каталога `DIR/<glob>`: `snapshot` (в пределах суток повтор не создаёт новую строку),
`purge` по правилу выше (`--dry-run` — только причина, без удаления; слепок пишется и в dry-run), в выбранный день
недели — `weekly` по последним 7 суткам. Вывод: строка JSON на каталог (`dir_name_sha16` вместо имени, `daily_uuid`,
число файлов, итог `purge`) и строка итога цикла; те же строки дописываются в лог (по умолчанию
`logs/quarantine_state.log`). Запуск по расписанию настраивается вне модуля (планировщик ОС).

## Метрики прогонов блоков (`record-run <file.json | ->`, таблица `run_metrics`)

Запись прогона — только числа и коды: `task` (код задачи, `B15`), `block` (`run`, `elevated`, `verify`, `st`…),
`started_at` / `ended_at` (ISO 8601), счётчики `steps`, `rollbacks`, `uac`, `hitl`, `parse_errors`, `net_errors`,
`flaky` (повторы упавших тестов в гейте; каждая повторная попытка — строка `FLAKY` в отчёте блока), `signal`
(1 / 2 / 3 / 5). Текст отчётов не хранится; лишние поля записи игнорируются. `run_id = uuid5(NAMESPACE,
sha256(канонический JSON {run: [task, block, started_at]}))` — повтор той же записи не создаёт строку. CLI принимает
объект или список; при ошибке любой записи (код 2) не пишется ни одна.

`weekly` добавляет по суткам ряды `run.count`, `run.duration_s`, `run.<счётчик>`, `run.green_pct` (доля прогонов
с сигналом 1) и `run.clean_pct` (доля прогонов без откатов, FLAKY, ошибок разбора и сети), в процентах — в тот же
поиск точек спада (`k · scale`). Сутки только с прогонами (без слепка карантина) входят в окно с `daily_uuid = null`;
без строк `run_metrics` недельный слепок прежний.

## Схема `run_metrics` v2 и закрытие блока

Новая база создаётся сразу в v2: счётчики допускают `NULL` (значение не выведено из машинных строк — не догадка),
добавлены `source` (`block` — строку записал сам блок при закрытии; `backfill` / `backfill_text_b15` — дозапись) и
`report_sha16`, `outcome` (`GREEN` / `RED` / `ROLLBACK` / `STOP` — сигнал 2 / `ASK` — 3 / `MANUAL` — 5),
`fail_stage` и `fail_code` (шаг и машинный код остановки; `NULL` у `GREEN`), `attempt` (номер попытки той же
задачи и блока за сутки — считается чтением таблицы при записи). Каждый запуск с любым исходом — своя строка:
`run_id` блока = `uuid5` от задачи, блока, времени старта и соли запуска; строка не перезаписывается (повтор того же
запуска — та же строка, другой запуск — новая). Базу v1 переводит только явная команда `migrate --backup-dir DIR`: сначала копия всей базы в `DIR`
(сверка числа строк), затем в одной транзакции новая таблица, перенос строк (`source = backfill_text_b15`,
`outcome` по сигналу, `attempt` по порядку старта) и замена;
на v2 команда ничего не делает. Запись в базу v1 отклоняется (код 3 у `record-run`). `NULL` в рядах недельного
слепка — «нет данных» (см. ниже). `read-run <run_id>` — строка по `run_id`.

Закрытие блока — `tools/block_finish.py --metrics FILE --db P` (логика — `src/block_finish.py`): вход — строки
`METRIC <ключ>=<значение>` (`task`, `block`, `started_at`, `ended_at`, семь счётчиков, `signal_wanted`,
`report_sha16`, `run_nonce`, `outcome`, `fail_stage`, `fail_code`; пустое значение — `NULL`, только при исходе не
`GREEN`), прочие строки не читаются. Закрытие вызывается на любом исходе, в том числе при откате и остановке до
действий. Итог `SIGNAL: 1` печатается только если строка `run_metrics`
(`source = block`) записана и прочитана назад новым соединением с теми же полями; иначе при `signal_wanted = 1` —
`SIGNAL: 3 - ASK; metrics_not_recorded (<причина>)`. RED / ASK / MANUAL не меняются; неразборчивый `signal_wanted`
— RED. Повтор с теми же строками даёт ту же строку и тот же итог; та же запись с другими полями — не GREEN.

## Серия искажений по стыкам (`tools/distortions.py`)

Суточные файлы `distortions_YYYY-MM-DD.json` (по умолчанию — рядом с базой): `series` (вид → число) и `by_boundary`
(стык → число), коды `[a-z][a-z0-9_]`, числа — целые или `null`; `notes` — короткие строки описания без текста
пользователя. `put --spec` — файл суток целиком (тот же итог — без записи; другой — только с `--replace`;
`"runs_from": "run_metrics"` — `runs` / `green` / `red` / `ask` / `manual` из базы), `add --event-id` — приращение
(повтор `event-id` без изменений), `day` — итог суток. `weekly` читает файлы окна: ряды `dist.<стык>` (`by_boundary`)
и `dist_kind.<вид>` (`series`); файл с нарушенной схемой пропускается (`dist_skipped`).

## Недельный слепок: «нет данных» и направление ряда

Точка ряда `null` — нет данных: суток нет в источнике ряда (нет слепка карантина / прогонов / файла искажений) или
счётчик суток неизвестен (хоть одна строка суток с `NULL`); внутри существующего источника отсутствующая категория
или стык — 0. Точки `null` не участвуют в медиане и MAD; при меньше чем 3 известных точках ряд — `insufficient`,
точки не ищутся. Направление «плохо» задаёт таблица `DIRECTIONS` (одно место в коде): рост — для искажений (стыки
и виды), `run.rollbacks`, `run.red` / `rollback` / `stop` / `ask` / `manual`, `run.parse_errors`, `net_errors`, `flaky`,
`uac`, `hitl`, `steps`, `duration_s` — ищутся всплески `x > median + k · scale`; падение — для `run.count`,
`run.green`, `run.green_pct`, `run.clean_pct` и рядов карантина — провалы `x < median − k · scale`. Ряд без
направления в поиск не идёт и попадает в `undirected` (тест требует, чтобы таких не было). В выдаче `weekly` —
`known` (число известных точек по ряду), `insufficient`, `undirected`; узел зума — с `direction`.

## Ретро-разбор (`import-retro <events.json>`) и вид строки

Строка `run_metrics` — запуск блока (`kind = block_run`) или инцидент вне блока (`kind = incident`: источник —
не код задачи вида `B29`, либо код с сомнением `B18j?`). Ряды блоков в недельном слепке считаются только по
`block_run` с сигналом; `run.not_started`, `run.incident` и ряды стыков `run_bnd.<стык>` — по всем строкам.
Событие ретро-разбора (`source = retro_audit`): `day`, `time` (как в источнике → `time_text`; точное `HH:MM` →
`started_at`, иначе `NULL`), код задачи / источника, блок, исход (`NOT_STARTED` для запуска, не начавшегося после
клика / UAC; у инцидента `FAIL` / `CAUGHT` / `WARN` / `WAIT` / `FOUND` / `NOT_STARTED`), `fail_code`, `boundary`,
`attempt` (или `NULL`). Текст описания не хранится; `report_sha16` — sha16 канонического события. Событие, которое
совпало с уже записанной строкой дозаписи (тот же день, код задачи, блок и attempt, время подходит, строка не
`GREEN`), не дублируется: у строки дополняются пустые `fail_code` / `boundary`, `source = backfill+retro_audit`,
исход строки не меняется (расхождение — в `conflicts` и пометка `retro_conflict = 1` у строки). Повтор импорта ничего не дублирует. Вывод: `total`,
`inserted`, `new_rows`, `matched`, `rejected` (индекс и причина), `conflicts`.

## Маячок запуска и ожидание человека

`launch_ts` — время маячка запуска (первый шаг скрипта блока, файл `started_<блок>_<ts>.flag`: время и pid).
`launch_delay_s` — от времени запроса до маячка, если блок знает время запроса; иначе `NULL`. `uac_wait_s` — от
запроса повышенных прав до появления отчёта повышенной части; `hitl_wait_s` — паузы, где блок ждёт решения
человека. Секунды; `NULL` — не измерялось, `0` — ожидания не было. Истёкший или отменённый запрос прав — исход
`NOT_STARTED` (сигнал 2), `fail_code` `uac_expired` / `uac_cancelled`. Ряды `run.launch_delay_s`, `run.uac_wait_s`,
`run.hitl_wait_s` (плохо — рост) появляются в недельном слепке, только если в окне есть хоть одно измерение.
